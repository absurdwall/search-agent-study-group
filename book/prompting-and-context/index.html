Study group guide · Chapter 3 Draft

From a Prompt to a Controlled Agent Run

One research request, progressively made observable and controllable

A study-group member asks an agent to compare current guidance from OpenAI and Anthropic for keeping agent context focused. The request sounds concrete, but it leaves consequential questions unanswered: Which sources count? What evidence is enough? What may the agent do, and how will it know when the comparison is finished?

A useful answer requires more than better wording. The system must decide what information reaches each model call, make its operating rules and observations usable, and control when research continues, stops, or returns to a person. This chapter follows that one request as those responsibilities become visible.

Prerequisite recap. One model call receives structured input and returns structured output. Of the task-specific information assembled during a run, only what enters model-visible context can directly shape that call's inference; surrounding code can still constrain what happens before and after it.

By the end, you should be able to reconstruct a bounded research-agent run: distinguish the current task prompt from selected context and harness controls, explain one responsibility overlap, and judge whether an explicit workflow graph would earn its complexity. No coding or framework experience is required.

Prompt, context, harness, loop, and graph are useful engineering lenses, not standardized layers. They can describe overlapping responsibilities in the same run. They are not a nesting order, and this chapter will not turn them into one.

Primary companion reading

  • OpenAI — Prompting The practical teaching baseline for describing a result, adding useful context, setting meaningful boundaries, and refining a result. Its checklist is guidance for OpenAI products, not a standard prompt schema.
  • Anthropic — Effective context engineering for AI agents The chapter's stable explanatory source for curating finite model-visible context across an agent run. Anthropic presents context engineering as an emerging practice, not a standardized layer.

1. Make the research task concrete

Key resource

  • OpenAI — Prompting Use “Prompting overview,” “Describe the result you need,” “Add useful context,” “Set boundaries that prevent real problems,” and “Improve the result with follow-up messages.”

Start with the request that initiates this run:

Compare current guidance from OpenAI and Anthropic for keeping agent context focused.

The topic is visible, but the intended result is not. The agent does not yet know the audience, the comparison dimensions, the evidence standard, the source limit, or which actions require restraint. A longer prompt is not automatically better; the useful additions are the ones that change what a successful result looks like.

A practical checklist, not a required schema

OpenAI's current Prompting guide suggests four useful questions for larger or important tasks: the goal, the context that will help, the desired output, and the boundaries that prevent real problems. It also says to use only the parts that help rather than treating the list as a rigid formula. OpenAI: Prompting overview

Goal
Help a study-group reader understand where the guidance agrees, where it differs, and what remains product-specific.
Useful context
The comparison dimensions, approved official source map, current source metadata, and any evidence already accepted or rejected.
Output
A short comparison with direct links, claim-level support, and explicit labels for product-specific conclusions.
Boundaries
Use no more than four approved official sources, do not generalize a product practice into a universal rule, and prepare a draft without writing or publishing to any external system.

This ordering matters. OpenAI recommends describing the result rather than prescribing every step, adding only information that can change the result, and focusing boundaries on the few mistakes that would make the work unusable. That leaves the agent room to search and compare while still making the result reviewable. OpenAI: Describe the result, add useful context, and set boundaries

In this checklist, useful context names information the user knows will matter. It does not mean that every named source or every retrieved page must be placed into the next model call. Section 2 will separate the request's source direction from the context the surrounding system actually assembles for each call.

Turn the request into a current-run specification

Current run specification

Compare current guidance from OpenAI and Anthropic for keeping agent context focused. Use no more than four sources from the approved official-source list. Produce a concise comparison with direct links; support each substantive claim and label product-specific conclusions. Prepare a draft only—do not write or publish to an external system. Before finishing, check that each comparison dimension has sufficient evidence and flag any unresolved conflict instead of guessing.

Same safety goal, different responsibilities. “Do not write or publish externally” is a user-requested boundary in this task prompt. The harness enforces a stronger capability boundary by exposing only read-only search and page-reading tools, while withholding or blocking tools that could write to external systems. The prompt states the user's intent; the harness controls what the run can actually do.

Iterate without reopening the whole task

A first prompt does not need to anticipate every problem. OpenAI's guide recommends reviewing the result and using a specific follow-up to add a missing source, correct the direction, or change the level of detail without starting over. OpenAI: Improve the result with follow-up messages

For this run, a bounded follow-up might say: “Keep the approved sources and comparison dimensions. Revise only the claims that lack direct support, and preserve the product-specific labels.” That is a correction to the current task, not permission to add new providers, broaden the research question, or keep iterating indefinitely.

The incoming request is the start trigger for this research run. That observation is enough for now. Section 5 will later distinguish a start trigger from the conditions that continue, retry, stop, or escalate a run already in progress.

2. Decide what this model call should see

Key resource

  • Anthropic — Effective context engineering for AI agents Use “Context engineering vs. prompt engineering,” “The anatomy of effective context,” and “Context retrieval and agentic search.”

Section 1 bounded the run. That specification is one candidate for the next model call, but it is not the whole context. Anthropic uses context for the set of tokens included when a language model produces an output. Those tokens can include instructions, tool definitions, selected source material, prior messages, and tool results—not just the user's latest prompt. Anthropic: Context engineering vs. prompt engineering

Context is therefore a model-call property. A page in storage, a search result the agent could open, and a passage actually placed before the model are three different states. Only the third is model-visible now.

Retrieval proposes; context selection admits

Three sets help make the decision visible:

Source universe
Everything the run could potentially inspect: the approved official pages, their sections, earlier notes, and any stored artifacts.
Retrieved candidates
The titles, snippets, metadata, or passages surfaced by search and reading tools because they might help with the current question.
Model-visible context
The smaller packet selected for this inference step: enough evidence and state for the model to make the next sound decision.

Retrieval can narrow the universe, but it does not settle what the model should see. A search may return five plausible passages. The system may admit two, retain one as a link for later, and reject two as duplicate or off-topic. Treating every retrieval result as context would make the retrieval ranking—not the task—decide how the model's limited attention is spent.

Anthropic describes context as finite and recommends the smallest high-signal set that still supports the desired outcome. “Smallest” does not mean mechanically short; it means every included item has a job in this call. Anthropic: The anatomy of effective context

A packet for one comparison decision

Suppose the agent has already found candidate passages about progressive disclosure. The next call only needs to decide whether OpenAI and Anthropic are describing the same mechanism. Its packet can be compact and explicit:

Visible in this call

  • the bounded research question and the comparison dimension: when detail becomes visible;
  • one directly relevant passage from each approved provider;
  • source title, date, URL, and product-specific labels;
  • accepted evidence, unresolved differences, and the remaining two-source budget;
  • the required output: decide whether the two passages support a shared principle or only parallel product examples.

Available, but excluded for now

  • pricing, installation, model benchmarks, and unrelated product features;
  • full navigation, repeated boilerplate, and duplicate snippets;
  • the complete text of pages whose relevant passages are already present.

The exclusions are not lost facts. They remain in the source universe and can be retrieved later if the question changes. Selection is a reversible focus decision, not deletion.

Selection question. What is the smallest high-signal packet that lets this model call make its next sound decision? The answer can change on the next call.

3. Start with a map, then load detail when needed

Key resources

  • Anthropic — Effective context engineering for AI agents Use “Context retrieval and agentic search” and the supporting long-horizon techniques.
  • Claude — The new rules of context engineering for Claude 5 generation models Use “Then: Put it all upfront / Now: Use progressive disclosure” as a current Claude Code product example, not a universal rule.
  • OpenAI — Harness engineering: leveraging Codex in an agent-first world Use “We made repository knowledge the system of record” for the map-not-manual case.

Section 2 selected a packet from information already surfaced. But a long-running agent also needs a way to discover information without loading every possible detail first. Progressive disclosure starts with a compact map—titles, paths, dates, section headings, short descriptions—and follows pointers only when the current decision exposes an evidence gap.

Anthropic describes a just-in-time approach in which agents retain lightweight references such as file paths, stored queries, and web links, then load the referenced data at runtime. The metadata itself helps the agent decide where to look next. Anthropic: Context retrieval and agentic search

Watch one evidence gap open and close

  1. Read the map. The agent sees four approved source records with provider, title, date, URL, product scope, and section headings. It does not receive four full articles.
  2. Notice the gap. The comparison state already supports “keep context focused,” but lacks direct evidence about when detailed guidance should be loaded.
  3. Load targeted detail. The agent opens Anthropic's “Context retrieval and agentic search” section and Claude's “Now: Use progressive disclosure” subsection, rather than their entire surrounding product pages.
  4. Update the working state. It records a supported shared principle—load relevant detail when needed—plus a caveat: deferred tool definitions and selectively called Skills are Claude Code examples, not requirements for every agent system.
  5. Release bulky detail. Direct links and concise claim notes remain; repeated navigation, unrelated sections, and raw passages no longer needed for the next decision stay outside the new context packet.

Claude's 2026 article reports moving code-review and verification guidance into selectively called Skills and deferring some tool definitions until search finds them. That is strong evidence for how one product implements staged loading, but the broader engineering idea does not depend on Claude Code or Skills. Claude: Then put it all upfront; now use progressive disclosure

OpenAI reports a related Codex case: a short AGENTS.md acts as a table of contents pointing into a structured repository knowledge base. The agent starts from a stable entry point and knows where to look next instead of receiving one monolithic manual. OpenAI: Give Codex a map, not a 1,000-page instruction manual

Keep a small state, not a second encyclopedia

Staged loading works only if the run remembers enough to avoid repeating itself. For this scenario, the working state can stay short: comparison dimensions, accepted claims with source pointers, rejected evidence with reasons, unresolved questions, and the remaining source budget. It is a navigation and decision record, not a copy of every page read.

Progressive disclosure
Controls when and how much external detail is loaded. It begins from a map and follows a pointer when the current task needs more evidence.
Compaction
Compresses context that has already accumulated so the run can continue with a smaller representation. Anthropic presents it as a long-horizon technique; it is not another name for staged loading.
Memory
Persists notes outside the current context. A memory becomes model-visible context only if the system later retrieves and selects it for a call.

Anthropic defines compaction as summarizing a conversation near its context limit and starting a new context with the summary. It describes structured note-taking, or agentic memory, as persisting notes outside the context window and pulling them back later. Both help long-horizon work, but neither collapses the distinction between stored information and current model-visible context. Anthropic: Compaction and structured note-taking

The run can now find and curate information, but a map does not enforce permissions, make tools legible, or verify that an action succeeded. Those surrounding guides and observable signals are the next lens: the Harness.

4. Put rules before action and evidence after it

Key resources

  • Birgitta Böckeler — Harness engineering for coding agent users The primary mental model for guides, sensors, computational and inferential controls, and an outer harness that users can shape.
  • OpenAI — Harness engineering: leveraging Codex in an agent-first world A concrete system case: tools, legible environments, repository knowledge, checks, observability, review, and recovery working together.
  • LangChain — The anatomy of an agent harness A deliberately broad supporting definition. Use it to see why the term overlaps with Context and Loop Engineering, not to impose a standard boundary.

The run now has a bounded task, a source map, and a way to load detail on demand. Yet none of those alone answers practical questions such as: Which tools can the agent call? How is a page read? What happens when a source is unavailable? Who checks that a claim has evidence? The Harness lens looks at the surrounding system that turns model output into usable action and returns observations for the next decision.

The term is still broad. LangChain uses harness for nearly everything around the model, including tools, state, infrastructure, orchestration, and hooks. Böckeler narrows the lens for coding-agent users: part of the harness is built into the product, while users can shape an outer harness for their own environment. These are useful viewpoints, not a settled industry boundary. LangChain: The anatomy of an agent harness Böckeler: A bounded user-harness view

Guide before action; sense after action

Böckeler's most useful distinction is directional. Guides are feedforward controls: they anticipate unwanted output and steer the agent before it acts. Sensors are feedback controls: they observe what happened and produce signals that can support correction. Guides without sensors cannot tell whether they worked; sensors without guides repeatedly rediscover preventable mistakes. Böckeler: Feedforward and feedback

Guides before the research action

  • an allowlist of four official sources;
  • a source-record shape requiring provider, title, date, URL, scope, and retrieved section;
  • the comparison dimensions and the rule to label product-specific evidence;
  • a citation format and a coverage threshold for sufficient support.

Sensor signals after the action

  • the page reader's HTTP status, final URL, publication date, and title;
  • allowlist pass or fail for every source used;
  • a citation-coverage result naming unsupported claims;
  • dimension-completeness status and a product-generalization flag.

Read-only search and page-reading tools are neither a Guide nor a sensor signal. They define the capability boundary: what actions the Harness makes possible. A check is the mechanism; its observed pass, failure, measurement, or flag is the signal that can guide a later decision.

Some controls are computational: deterministic checks such as URL validation, allowlist enforcement, schema validation, and link coverage. Others are inferential: model-based judgments such as whether two claims genuinely agree or whether a caveat is adequate. Böckeler recommends distinguishing the two because they differ in speed, cost, and reliability. Böckeler: Computational vs. inferential controls

Use a cheap deterministic check to produce the sensor signal wherever the question is deterministic. “Is this URL on the allowlist?” should not be left to model judgment. Use an inferential review where meaning matters, and keep the resulting signal's uncertainty visible. “Does this paragraph overgeneralize a Claude Code practice?” needs semantic review, not a string match.

The overlap with context is a handoff, not an identity

A guide can become model-visible context: the harness may place the source schema or comparison dimensions into a call. A sensor result can also become context: the next call may receive “claim 3 lacks an approved citation” and revise it. But the harness includes machinery that never needs to appear as tokens—the code that withholds write tools, executes the page reader, validates the allowlist, or routes a failed check back for correction.

One overlap to remember. Context Engineering decides which guide or sensor signals the model sees now. Harness Engineering decides how those guides, capabilities, observations, and checks are made available and enforced around the model.

Why the OpenAI article feels larger than “how to build a harness”

OpenAI's Harness Engineering article is a case study, not a component tutorial. It describes a whole agent-first development environment: repository-local knowledge, browser access, logs and metrics, custom linters, structural tests, review loops, and recovery. Its teaching value is the interaction among those pieces. A task prompt alone did not create reliable work; the environment made the application's state legible and supplied feedback the agent could act on. OpenAI: Increasing application legibility and enforcing invariants

That is also why the article can feel like it “doesn't teach harness engineering.” It shows the accumulated result of engineering a harness, while Böckeler supplies a smaller diagnostic vocabulary for designing one control at a time: What should guide the agent before action? What can sense the result afterward? Which signal should trigger self-correction, and which still requires a person?

Sensors make correction possible, but they do not decide by themselves how many times the system should try. That is the next lens: the Loop—the run's explicit rules for continuing, retrying, stopping, and escalating.

5. Let the run continue—and make it stop

Key resources

  • Claude — Loop engineering: Getting started with loops A current Claude Code taxonomy organized by trigger, stop condition, product primitive, and task fit. Use the taxonomy as a product example.
  • Addy Osmani — Loop Engineering An emerging practitioner framing for designing the recurring system around agent work, durable state, verification, and human ownership.

A Harness can provide tools and feedback, yet one unanswered control question remains: after a sensor reports a gap, does the system try again? Loop Engineering focuses on the repeated cycle of work and the decisions that govern it. The Claude Code team defines a loop as an agent repeating cycles of work until a stop condition is met. That definition is useful, but the product commands and four loop types in its article are Claude Code's current taxonomy—not a standard that every system must copy. Claude: Getting started with loops

Five decisions, not one circular arrow

Start
The user's bounded comparison request creates a new run with an empty evidence record and a four-source budget.
Continue
A required comparison dimension still lacks evidence and there is a relevant approved source or section that has not been examined.
Retry
The intended action failed in a way that may be transient—for example, a page read timed out—so the same action may be attempted again under a retry cap.
Stop
Every required dimension is supported or explicitly marked “no comparable claim found,” citations and labels pass, and no unresolved conflict blocks a truthful draft.
Escalate
The source budget is exhausted, official sources conflict, a required page remains unavailable after retry, or resolving the issue needs a new source or broader authority.

These decisions must remain separate. A missing claim is a reason to continue research, not automatically to repeat the same failed request. Exhausting the budget is not successful completion. Needing a human judgment is not a failure to stop; it is a different exit with a useful handoff.

The loop reads and writes explicit state

Repetition is only controlled when each pass can inspect what earlier passes established. For this run, the durable state is deliberately small:

Research state after one pass

Dimensions
focus principle: supported · loading timing: partial · verification: unresolved
Evidence
2 accepted claims · 1 Claude-specific example · 1 rejected duplicate
Budget
2 of 4 sources used · first OpenAI read failed · one retry remains
Next decision
retry the same OpenAI verification-section read once; do not reopen context-window background

The cycle is then concrete: select the next evidence gap, assemble a focused context packet, act through the Harness, observe sensor results, update state, and choose an exit or another pass. Prompt, Context, and Harness responsibilities participate in the Loop; none of them is replaced by it.

Completion needs a second boundary: cost

A success condition prevents premature stopping. A budget prevents endless pursuit of that condition. This chapter's run has both: at most four approved sources, at most one retry for a failed page read, and no new provider or external write without human approval. If the evidence standard cannot be met inside those limits, the correct output is an escalation packet describing what is known, what was tried, and which decision is needed.

Claude's loop guidance similarly recommends explicit success and stop criteria, turn caps for goal-based loops, pilot runs before large executions, and matching schedules to how often the observed system changes. Those are current Claude Code recommendations; the general lesson is to budget repeated work in the unit your system can actually measure—turns, attempts, tokens, time, sources, or money. Claude: Managing token usage

Choose the smallest loop that fits

Claude's product article distinguishes turn-based, goal-based, time-based, and proactive loops by what triggers them, what stops them, and what the user hands off. That comparison is helpful for adoption decisions even outside Claude Code, as long as its commands are not mistaken for universal mechanisms. Claude: Loop types and handoff

Which loop fits this research task?
Pattern What is handed off Fit here
Turn-based The agent acts and checks; the person decides the next turn. Safe default while the comparison method is still being learned.
Bounded goal-based The stop decision, within explicit evidence and cost limits. Best fit for this run once the completion checks are trusted.
Time-based The trigger repeats on an interval. Poor fit: this is a one-time comparison, not a monitoring task.
Proactive The recurring prompt or workflow runs without a person present. Unnecessary until there is a stable stream of updates to process.

Addy Osmani's recent Loop Engineering essay pushes the same leverage point further: design the system that repeatedly supplies work, preserves state, separates making from checking, and returns anything it cannot handle to a person. He also warns that a smooth loop can accelerate mistakes and understanding loss. This is an emerging practitioner framing, not a settled discipline; its most durable contribution here is the insistence that the human still owns the outcome. Osmani: What one loop looks like and what it still does not do

This run has one normal cycle and a handful of explicit exits. We can still explain it without a framework. The next question is not “Can it be drawn as a graph?”—almost any process can—but “Would an explicit graph make its branching, state, recovery, or handoffs easier to control?”

6. Decide whether the control flow needs a graph

Technical anchor

  • LangGraph — Graph API overview A concrete implementation vocabulary for state, nodes, normal and conditional edges, start and end points, and explicit routing. This chapter uses the vocabulary for an adoption decision, not a framework tutorial.

The Loop in Section 5 can already be drawn as circles and arrows. That does not mean it needs a graph runtime. The Graph lens becomes useful when naming steps, state, and routes makes a complicated flow easier to inspect, resume, test, or hand off.

LangGraph's Graph API describes three core components: shared state is the current application snapshot; nodes perform work and update that state; and edges choose what runs next, either through fixed transitions or conditional branches. Nodes do not have to be model calls; they can also be ordinary deterministic functions. LangGraph: State, nodes, and edges

This vocabulary is valuable even if the final system is implemented with a small loop and a few functions. It forces the design to name where state changes and who owns each routing decision. But adopting a graph framework also adds schemas, routing code, persistence choices, debugging surfaces, and migration work. Explicitness must repay that cost.

Ask what the graph would make safer or clearer

Signals that can justify an explicit workflow graph
Signal What becomes explicit Present in this run?
Several meaningful branches Different evidence types or failures route to different work, not merely “try again.” No. The next step is always the highest-priority unresolved dimension.
Persistent checkpoints The system can stop, resume, inspect, or recover from a named state boundary. Not required. The comparison is short enough for one bounded run.
Pause for human input A handoff node records the question and later resumes the correct path. Only as a terminal escalation; resuming inside the same run is optional.
Separate citation gates Drafting, claim verification, product-specificity review, and repair have distinct routes. One compact verification pass is sufficient at current scope.
Parallel work and join Provider-specific research branches can run separately and reconcile into shared state. Unnecessary for four sources; coordination would cost more than it saves.

The decision for this chapter's run: no graph yet

Keep the current implementation as one bounded loop with an explicit state record and four exits. It has one main work path, a tiny source budget, one retry policy, and terminal human escalation. A graph drawing may help teach the flow, but a graph runtime would not yet remove meaningful ambiguity.

Adoption rule. Use a graph when named state transitions, branching, pause-and-resume, recovery, parallel joins, or human handoffs need to become first-class system behavior—not because “Graph Engineering” sounds like the next layer.

The decision would change if this one-time comparison became a maintained guidance monitor. Imagine that provider updates arrive on different schedules, each provider gets a separate research branch, citation failures route to targeted repair, contradictory guidance pauses for editorial judgment, and a checkpointed run resumes after approval. Now named nodes and conditional edges clarify responsibility:

  1. Detect update records the changed official source.
  2. Research provider loads only the affected guidance and updates evidence state.
  3. Verify claims routes clean claims forward and citation failures back to repair.
  4. Resolve conflict interrupts for a person when providers cannot be compared truthfully without editorial judgment.
  5. Publish candidate prepares—but still does not automatically publish—the approved comparison.

LangGraph documents conditional edges for routing from current state, checkpoint-based persistence for recovery, and interrupts that pause execution and resume with external input. Those are examples of capabilities that can justify graph adoption when the workflow truly needs them; they are not evidence that every agent should use LangGraph. LangGraph: Conditional edges and resume commands LangGraph: Interrupts and persisted resume

We now have five lenses and one explicit non-adoption decision. The final test is whether the reader can assign every part of the actual run without turning those lenses into a hierarchy.

7. Reconstruct the complete research run

The five terms are useful only if they help diagnose a real system. Rebuild this chapter's run from its responsibilities rather than from a memorized stack diagram.

The run, end to end

  1. Specify. The user asks for a concise comparison of current OpenAI and Anthropic guidance, limited to four approved official sources, with direct support and product-specific labels.
  2. Map. The system exposes a compact source record for each approved page: provider, title, date, URL, scope, and section headings—not every page in full.
  3. Select. For the current comparison dimension, the system admits the bounded task, two relevant passages, evidence state, and remaining budget into the model call.
  4. Act. The agent chooses a read-only page-reading tool and opens the next relevant section. No external write capability is available.
  5. Observe. Deterministic checks return page metadata, allowlist status, and citation coverage; semantic review flags any unsupported generalization.
  6. Update. The run records accepted and rejected evidence, unresolved dimensions, retry count, and source budget. Bulky page detail remains outside the next packet unless needed.
  7. Decide. The controller continues to a new evidence gap, retries one transient read failure, stops with a supported draft, or escalates a conflict or exhausted budget to the user.
  8. Keep it simple. Because those decisions form one short path with small state and terminal escalation, the run does not adopt a graph runtime.

Assign each responsibility

A responsibility map for the controlled research run
Lens Question it answers here Concrete responsibility
Prompt What result is this run trying to produce? States the comparison goal, useful task context, output requirements, evidence boundary, and requested no-write restraint.
Context What does this model call see now? Selects the smallest high-signal packet from task, map, passages, prior observations, and working state.
Harness What surrounds the model so work is possible and observable? Exposes read-only tools, enforces the allowlist and capability boundary, runs checks, and returns sensor signals.
Loop Why does the run take another pass—or exit? Reads state and budget, then distinguishes continue, bounded retry, successful stop, and human escalation.
Graph Would explicit nodes, state transitions, and routes repay their complexity? Records a no-adoption decision now and names the future branching, persistence, recovery, and handoff signals that could change it.

Explain one overlap without inventing layers

After citation coverage fails, the Harness produces a deterministic sensor signal: “comparison claim 3 has no approved source.” Context Engineering selects that signal, the relevant claim, and the source map for the next model call. The Loop reads the updated failure state and chooses another evidence pass. One event crosses three lenses; no lens contains the others.

The same is true of the Prompt's no-write boundary. It communicates user intent inside the task. The Harness enforces the capability by withholding write tools. The Loop escalates rather than inventing a write path if external publication later becomes necessary. Shared safety goal, different responsibilities.

Run the reconstruction test yourself

Checkpoint

Imagine the Anthropic page loads, but its relevant statement is a Claude Code-specific practice; the OpenAI page times out once; two sources remain in budget; and the “verification” comparison dimension has no supported OpenAI claim yet.

  1. What should be visible in the next model call, and what should remain outside it?
  2. How should the source map support progressive disclosure at this evidence gap?
  3. Which instruction is a Prompt responsibility, and which restriction must the Harness enforce?
  4. Which Guide, capability boundary, checks, and sensor signals should the Harness provide?
  5. Does the Loop continue, retry, stop, or escalate—and why? Explain one responsibility overlap along that path.
  6. Does this new state justify a Graph? Name the specific adoption signal if you think it does.
Compare your reconstruction

The next call should see the bounded task, the unresolved verification dimension, the Claude-specific passage and label, the failed OpenAI URL with retry count, the compact source map, accepted evidence, and the two-source budget. Unrelated page sections and full prior tool output stay outside. The compact map keeps those sections discoverable; progressive disclosure follows only the OpenAI verification pointer exposed by this evidence gap.

The Prompt states the official-source, product-label, and no-write requirements. The Harness enforces the official allowlist and read-only capability boundary, runs the page and coverage checks, and returns final URL, status, unsupported-claim, and product-generalization signals. The Loop—not the Harness—takes the bounded retry path for the transient OpenAI read. If it fails again, it escalates rather than spending a new source or claiming the dimension is complete.

One overlap crosses three lenses: the Harness returns the failed read signal; Context selects that signal, retry count, source pointer, and unresolved dimension for the next call; the Loop reads that state and chooses the permitted retry.

This alone still does not justify a Graph: it is one known retry edge and one terminal escalation. A persisted pause followed by later human approval and resume, several provider-specific repair branches, or parallel research that must join would be concrete signals to reconsider.

Chapter takeaway. Engineer the task-specific result with the Prompt, the current decision surface with Context, the surrounding capabilities and feedback with the Harness, repeated progress and exits with the Loop, and explicit workflow structure with a Graph only when its complexity earns its keep.
