From a Prompt to a Controlled Agent Run

A companion guide to three current resources

Good prompting for agentic work is not about discovering a magic phrase. It is about making the desired result legible, supplying the context that can change that result, naming the few boundaries that matter, and staying in the conversation while the work develops.

This chapter does not introduce a new prompting framework. It follows three selected resources and connects the parts that are easiest to miss when they are read separately. OpenAI supplies the practical sequence. Claude Code adds the working habits of verification, investigation, and course correction. Anthropic's Claude 5 article asks what should change when a more capable model needs fewer rules and can discover more context for itself.

Read alongside this chapter

  1. OpenAI — Prompting Living documentation. The chapter follows its result → context → output → boundaries → follow-up sequence.
  2. Anthropic — Best practices for Claude Code Living documentation. Use it for verification, exploration, concrete references, communication, and session management.
  3. Anthropic — The new rules of context engineering for Claude 5 generation models July 24, 2026. A model- and product-specific corrective lens on rules, judgment, progressive disclosure, and references.

One practical boundary. A prompt asks for something in the current interaction. Context is the wider material the model receives with that request. A harness surrounds the model with tools, state, and controls. A loop decides whether and how work runs again. These are useful working terms, not standardized layers.

By the end, you should be able to revise one of your own important prompts, decide what supporting material belongs with it, add a readable check, steer the work as it unfolds, and explain when the problem has moved beyond prompting.

1. Start with the result

Follow in the main reading

OpenAI — “Prompting overview” and “Describe the result you need”

OpenAI begins with a deliberately undramatic idea: a prompt can be a question, an instruction, or a goal, and it does not need technical syntax or a rigid formula. For larger or more consequential work, four components may help. OpenAI: Prompting overview

Goal
What should the agent know, make, change, or decide?
Context
Which facts, sources, files, or circumstances could change the result?
Output
How will the result be used, and what form will make it usable?
Boundaries
What must remain unchanged, be avoided, or return for approval?

This is a checklist, not a form. A short question may need only a goal. A consequential task may need all four. The useful test is not “Did I fill every field?” but “Would this detail change the work or prevent a costly mistake?” OpenAI explicitly advises using only the components that help.

Describe the outcome before prescribing the route

The guide's next move is to describe the result rather than dictate a long sequence of steps. Audience and format belong in the prompt when they change the deliverable. Process belongs there when the process itself is part of the requirement. Otherwise, a capable agent benefits from room to inspect, compare, and adjust its approach. OpenAI: Describe the result you need

Prefer an observable result. “Produce a one-page update for leadership with decisions and next steps first” tells the agent what success should look like. Add a required method only if following that method is itself part of success.

Claude Code's guide reaches the same conclusion from coding work. It recommends a separate plan when the approach is uncertain or the change crosses several files, but says to skip that overhead when the diff is obvious and small. Planning is a response to uncertainty, not a ceremony. Claude Code: Explore first, then plan, then code

2. Add useful context, not all available context

Read these sections together

  • OpenAI — “Add useful context”
  • Claude Code — “Provide specific context in your prompts”
  • Claude 5 — “Then and now” and “Applying this to your context”

OpenAI defines useful context as information that could change the result. That may be a document, spreadsheet, screenshot, current web source, project folder, or connected source. It also recommends naming what the agent should find rather than spelling out every search it should run. OpenAI: Add useful context

Claude Code makes this concrete for a codebase: identify the relevant file or scenario, state the constraint, point to an existing pattern, describe the symptom, and provide a checkable version of “fixed.” Rich context can arrive as referenced files, images, documentation URLs, command output, or material the agent retrieves itself. Claude Code: Provide specific and rich context

A prompt is only part of what the model receives

Anthropic's Claude 5 article widens the lens. In Claude Code, the user message is assembled with a system prompt, repository guidance, Skills, memory, tool definitions, and references. The exact mixture is product-specific, but the practical lesson travels: do not assume the current message is the entire context, and do not repeat everything in every message. Anthropic: The prompt is only a small part of context

Current request
Task-specific goal, sources, desired output, and immediate boundaries.
Persistent guidance
Stable project conventions or non-obvious gotchas that should apply across relevant work.
On-demand references
Detailed specs, examples, mockups, tests, or procedures that are useful only when the task reaches them.

Chapters 2 and 4 explain the mechanisms that can store and load this material. Here the important editorial decision is simpler: put specific task information close to the task; keep durable guidance small; make deep material easy to find instead of forcing all of it into every call.

Progressive disclosure changes what “provide context” means

The Claude 5 article reports that Anthropic removed more than 80% of Claude Code's system prompt for its newer models without a measurable loss on its coding evaluations. Its recommended shift is from putting all guidance upfront to making the right detail discoverable at the right time. It applies that idea to tools, Skills, persistent project guidance, and references. Anthropic: Progressive disclosure and simplifying context

“Rich references” can be more precise than more prose. A test suite can specify behavior; an existing function can specify a porting target; an HTML mockup can specify a design. This does not mean examples are generally bad. Anthropic's narrower warning is that tool-use examples can confine exploration when a clear, expressive interface would carry the requirement better.

3. Set meaningful boundaries—and give the work a check

Protect against the mistakes that would actually matter

OpenAI describes boundaries as the few instructions needed to prevent extra work or an unintended action: preserve approved facts, use only supplied sources, stay inside a budget, or draft without sending. It recommends focusing on the one or two boundaries that matter most instead of controlling every step. OpenAI: Set boundaries that prevent real problems

This restraint matters more for stronger agents, not less. Anthropic found that rules accumulated across the system prompt, project files, Skills, and user requests could conflict. Its Claude 5 guidance shifts from absolute rules toward instructions that let the model use the surrounding evidence and match the work at hand. Anthropic: Unhobbling Claude and rules → judgment

Important distinction. “Prepare a draft; do not send it” is a prompt boundary. A system that does not expose a send action, requires approval, or blocks the action in code is enforcing that boundary. Prompting can request restraint; it does not by itself guarantee it.

Make success observable

OpenAI recommends asking for a final check on important work and then reviewing the result yourself. Claude Code puts verification first: give the agent a test, build, lint result, fixture diff, or screenshot comparison it can read. Without such a signal, “looks done” is the agent's only stopping condition and the human becomes the whole verification loop. OpenAI: Make the result ready to use Claude Code: Give Claude a way to verify its work

  • For factual work: direct sources, reconciled numbers, and explicit unknowns.
  • For code: a reproduced failure, the smallest relevant tests, and the build or lint command.
  • For a visual change: a target reference, a rendered comparison, and a list of remaining differences.
  • For a deliverable: a check that required sections agree and every named requirement is present.

Verification is strongest when the signal can disagree with the agent. “Tell me you finished” asks for another assertion. “Run this check and show the result” creates evidence. Deterministic gates, independent reviewers, hooks, and eval systems go further, but their mechanics belong to Chapter 5.

4. Explore before committing—when uncertainty earns it

Claude Code recommends separating exploration and planning from implementation when the approach is uncertain, the code is unfamiliar, or the change crosses several files. Its full coding workflow is explore, plan, implement, and commit, but the guide explicitly says that small, obvious changes should go directly to implementation. Claude Code: Explore first, then plan, then code

OpenAI expresses the same judgment in surface-neutral terms: ask for a plan when the approach matters, separate required work from optional polish, and require approval before the agent sends, publishes, or changes information that other people rely on. For Codex, a useful prompt points to the relevant code or reproduction steps and states how to verify the change. OpenAI: Prompting for ChatGPT Work and Codex

Use questions, references, and prototypes to expose unknowns

An agent can investigate a codebase, ask the questions you would ask another engineer, or interview you before drafting a specification. Claude Code recommends a fresh implementation session after a large interview so execution begins with a self-contained spec and clean context. That is a product workflow, but the portable lesson is to surface consequential unknowns before an expensive commitment. Claude Code: Communicate effectively

Optional companion

Anthropic's Fable field guide uses the familiar known/unknown matrix to suggest a blind-spot pass, interviews, references, brainstorming, and prototypes. Use these as discovery moves when uncertainty is material—not as required stages for every prompt.

5. Prompting continues during the run

OpenAI says the first prompt does not need to be perfect. Review the result, then ask for the specific change you need: add a missing source, correct the direction, request another option, or change the level of detail. In Codex, a follow-up can steer the active run or be queued for the next run. Those controls are product-specific; the general lesson is that prompting is an iterative conversation, not a one-shot artifact. OpenAI: Follow-up messages, steering, and queuing

Claude Code similarly recommends correcting direction as soon as you notice drift. It also advises starting fresh between unrelated tasks and clearing a session that has accumulated repeated failed approaches. For longer work, its product can compact, rewind, checkpoint, and resume conversations. These are different controls, but they serve one editorial goal: preserve the decisions that matter and release context that no longer helps. Claude Code: Manage your session

Correct: “The audience is new to this topic; define the terms before comparing them.”

Add: “Use this source as the authority for the current behavior.”

Narrow: “Stop the optional polish. Finish only the required sections and report what remains.”

A useful follow-up changes the work. Repeating the original request more loudly usually does not. If the agent has gone wrong several times, the better prompt may be a fresh one that incorporates what you learned, not another correction layered on top of the failed history.

6. Put the pieces together

OpenAI's complete project-update example combines the four optional prompt components and ends with a final check, without dictating every intermediate step. Read the full source example, then notice what each sentence does.

  1. Result: a one-page update for a named meeting and audience.
  2. Context: the latest plan and relevant decisions from connected sources.
  3. Output: decisions first, followed by progress, risks, owners, and dates.
  4. Boundaries: preserve approved facts, flag conflicts, and do not publish.
  5. Check: confirm that every next step has an owner and due date.

Claude Code would deepen the same prompt for an agentic task by adding the exact files or symptoms, an existing pattern to follow, and a check the agent can run. The Claude 5 article would ask whether any accumulated rules can be removed, whether a reference carries the requirement better than prose, and whether detail can remain discoverable until it is needed.

Before you send

  • Is the result clear enough to recognize?
  • Did you include only context that can change it?
  • Would a file, test, mockup, or existing pattern communicate better than more explanation?
  • Which one or two mistakes justify explicit boundaries?
  • What evidence can the agent show before it stops?
  • Where will you intervene if the work changes direction?

Do not solve every need by making the prompt longer

A fact specific to this task belongs near this task. A stable project convention may belong in persistent guidance. A detailed method may belong in an on-demand Skill or reference. A safety-critical action may need permissions or deterministic enforcement. A repeated job may need a loop. The prompt remains important, but it should not carry the entire system by itself.

7. Two short steps beyond prompting

Harness engineering

LangChain's broad formulation is Agent = Model + Harness: the harness is the surrounding code, configuration, and execution logic that gives the model state, tools, a filesystem or sandbox, feedback, and enforceable constraints. In that framing, harness engineering works backward from a behavior the agent needs and designs the surrounding system that makes the behavior possible or dependable. LangChain: The Anatomy of an Agent Harness

This is a useful, deliberately wide perspective—not a standard boundary accepted by every agent framework. For this chapter, the key transition is that a prompt can request verification or restraint, while a harness can provide the tool, environment, state, approval, or deterministic check that makes it operational.

Loop engineering

Addy Osmani uses loop engineering for a system that repeatedly finds work, assigns it, checks it, records what happened, and decides what comes next—effectively designing the system that prompts the agent. He places that system “one floor above” the single-run harness and emphasizes durable memory outside one conversation. Addy Osmani: Loop Engineering

Treat this as an emerging practitioner framing. The article is intentionally speculative, warns about token cost, and names a product-specific collection of automations, worktrees, Skills, connectors, subagents, and memory. Direct prompting remains the right tool for many bounded tasks; a loop earns its machinery only when work truly needs to recur and can be checked safely.

Practice: reconstruct one prompt you actually need

Choose a consequential prompt you expect to use next week. Do not make it longer yet. First annotate what is already there.

  1. Underline the requested result. Is the audience or use visible?
  2. Circle the context that could change the result. Remove context that cannot.
  3. Name the expected output and the one or two boundaries that prevent real problems.
  4. Write one check whose evidence the agent can show you.
  5. List the material the agent should inspect on demand instead of receiving upfront.
  6. Write one follow-up that would correct direction without restarting the task.
  7. Mark anything that cannot be made reliable by wording alone. Does it require persistent guidance, a reference or Skill, harness enforcement, or a recurring loop?

If you can explain those choices, you have reconstructed the central argument of all three companion readings without turning any one product's advice into a universal formula.
