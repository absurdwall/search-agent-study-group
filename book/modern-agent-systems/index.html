A Map of Modern Agent Systems

Instruction files, MCP, and Skills

Work in progress

This chapter is still being developed and reviewed. Its explanations, examples, and visuals may change before the chapter is ready for publication.

Chapter 1 explained a minimal agentic system: an LLM can propose tool calls, surrounding software executes them, and the loop carries results into later model calls. Modern products add several ways to make that system fit a project. This chapter focuses on three: instruction files, MCP, and Skills.

Imagine asking a coding agent to update the Week 3 page in this study-group repository, verify every external reference, and explain what changed. The minimal loop can inspect files, call tools, observe results, and continue. Three practical questions remain:

  • How does it learn the durable rules of this repository?
  • How can it connect to an approved external system in a reusable way?
  • How can it follow a repeatable chapter-review method without loading that entire method into every task?
Three different jobs around the minimal agent
Mechanism Primary job A useful question
Instruction file Durable guidance for a project or path. “What rules apply while I work here?”
MCP A shared connection protocol for external capabilities and information. “How can this host connect to that provider?”
Skill A reusable method with instructions and optional supporting resources. “How should this kind of task be carried out?”

This is a teaching map, not a universal product taxonomy. The three mechanisms can work together, but none is a required stage of the Chapter 1 loop. OpenAI and Anthropic place them beside other features, while their filenames, discovery rules, activation behavior, and interfaces remain product-specific. OpenAI: Customization; Anthropic: Extend Claude Code

1. Instruction files

A user request explains the current task. A repository also has guidance that should survive across tasks: where content belongs, which commands validate a change, what style the team follows, and which decisions remain with a human. Repeating those rules in every request is fragile. An instruction file gives a compatible host a known place to discover them.

How instruction files work

The basic pattern is simple: place ordinary Markdown at a known path; the host discovers relevant files; the host applies its own scope, composition, and precedence rules; and the resulting guidance becomes part of the active model context. The Markdown may be easy to share, but the loading behavior is a product feature—not a property of Markdown itself.

AGENTS.md is an open convention for repository guidance. Its format site describes root and nested files, but individual products decide how they search for and combine them. AGENTS.md: Official format site

Example repository
study-group/
├── AGENTS.md                 # rules for the whole repository
├── book/
│   └── AGENTS.md             # rules for book chapters
├── frontend/
│   └── AGENTS.md             # frontend-specific guidance
└── backend/
    └── AGENTS.md             # backend-specific guidance

If work happens under book/, a compatible host may use both the root guidance and the closer book guidance. It should not load frontend/AGENTS.md merely because that file exists. The exact resolution rule still depends on the host.

One convention, several product loaders

Repository guidance is portable only up to the host boundary
System Typical files Loading behavior to remember
Open convention AGENTS.md Defines a readable repository convention and broad nesting idea; it does not force every product to load files identically.
OpenAI Codex AGENTS.md, AGENTS.override.md, configured fallbacks Builds a chain from global guidance and the project root down to the working directory, with closer files later in the combined prompt.
Claude Code CLAUDE.md, CLAUDE.local.md, .claude/rules/ Uses its own additive hierarchy, imports, path-scoped rules, and managed locations. CLAUDE.md is a native system, not merely a renamed AGENTS.md.
GitHub Copilot .github/copilot-instructions.md, path-specific instruction files, and supported agent-instruction filenames Supports repository-wide and path-specific instructions with product-specific precedence and feature coverage.

Claude Code reads CLAUDE.md, not AGENTS.md directly. A repository that wants one shared source can import @AGENTS.md from CLAUDE.md, keeping Claude-specific guidance below the import, or use a symbolic link when no additions are needed. These choices can share guidance; they do not make the loaders identical. Codex, Claude Code, and GitHub Copilot still apply their own discovery, scope, and precedence rules. OpenAI: Custom instructions with AGENTS.md; Anthropic: How Claude remembers your project; GitHub: Repository custom instructions

What belongs in an instruction file?

Put durable, frequently relevant guidance close to the work it governs: validation commands, architecture boundaries, ownership rules, and links that route the agent to deeper documentation. Do not turn an always-loaded file into an encyclopedia of every procedure the project might ever use.

Boundary with Skills: an instruction file answers “what should remain true while I work here?” A Skill answers “how should I perform this particular kind of task?” A short rule can point to a Skill when a detailed, reusable procedure is needed.

2. Model Context Protocol (MCP)

Chapter 1 treated a tool as a capability the model can request. That leaves an integration problem: without a shared protocol, each AI host and each external provider may need a custom adapter. Anthropic introduced MCP in November 2024 as an open response to those fragmented one-off connections. Anthropic: Introducing MCP

MCP standardizes the connection and exchange boundary. It does not replace the agentic loop, define the model's judgment, or turn every connected operation into the same tool.

Host, client, and server

In the versioned 2026-07-28 architecture, an MCP host is the AI application. It creates an MCP client for each connected MCP server. A server may run locally or remotely. The protocol separates a data layer from the transport layer and defines primitives such as tools, resources, and prompts. MCP: Architecture overview, 2026-07-28

The protocol participants are not the agentic loop
Participant Responsibility Not automatically responsible for
Host Coordinates clients and decides how the AI application uses connected capabilities. Trusting every server or approving every action.
Client Maintains the protocol connection to one server for the host. Choosing the agent's overall task strategy.
Server Provides protocol-accessible tools, resources, prompts, or extension capabilities. Being an agent, model, or complete workflow.

A concrete connection

Suppose the Week 3 update needs issue data from an approved remote system. One simplified run looks like this:

  1. Connect. The host establishes an authenticated client connection to the approved server.
  2. Discover. The client asks what the server currently provides.
  3. Select. The host filters that catalog and makes only relevant capabilities available to the model.
  4. Propose. Inside the existing Chapter 1 loop, the model proposes a call to one exposed tool.
  5. Execute. The host routes the request through the client; the server performs the operation.
  6. Observe. The result returns to the host, which decides what enters the next model context.

This is one host's implementation pattern, not the whole protocol. OpenAI's current MCP integration, for example, supports remote servers, imported tool lists, allowed-tool filters, approvals, and OAuth while warning developers to treat remote servers as a trust boundary. OpenAI: MCP and Connectors

Tool and MCP are different levels
Tool MCP
Describes an operation the model can request. Defines how a host and external provider connect, discover capabilities, and exchange messages.
May be built into the host, local code, or exposed through another integration. May carry tools, but also resources, prompts, and extension capabilities.
Does not imply MCP. Does not imply that every server capability is exposed to the model at once.

What MCP does not solve

Interoperability does not determine whether a server is trustworthy, which actions require approval, or how authentication, prompt injection, context selection, execution safety, and stopping are handled. Those responsibilities remain with the host, application policy, execution environment, and human reviewers.

MCP's evolving frontier

Stateless MCP

In the 2026-07-28 protocol, each request carries its protocol version and relevant capabilities, so a server does not need a protocol-level MCP session to interpret the request. Removing earlier protocol-session management burdens simplifies clients and servers, avoids requiring sticky routing to a specific backend, and fits horizontally scaled remote services more naturally. Transport connections and notification streams can still remain open, and an application may still maintain explicit task or domain state. The official architecture defines the behavior; Simon Willison supplies a practitioner interpretation of its operational consequences. MCP: Architecture overview; Simon Willison: Stateless MCP

Code execution with MCP

Direct tool calling works well for a small relevant catalog: the model sees a tool definition, proposes a call, and receives the result. At larger scales, eagerly loading many schemas and sending every intermediate result through the model can waste context. A code-execution pattern instead lets the model write a bounded program that discovers selected operations, composes several calls, filters or joins results, and returns only the useful subset.

This is an architectural pattern layered around MCP, not part of the MCP protocol. It also introduces requirements for sandboxing, resource limits, monitoring, and safe data handling. Anthropic: Code execution with MCP

MCP Apps

MCP Apps is an official extension that lets a tool return an interactive interface to a supporting client. A form, dashboard, chart, or multi-step control can appear inside the conversation instead of reducing every interaction to text or raw JSON. It is an extension, not part of the minimal core protocol. MCP Apps: Bringing UI capabilities to MCP clients

The official MCP Registry

The Registry addresses another emerging need: how people and hosts discover metadata about published MCP servers. It is preview infrastructure for an ecosystem, not a completed universal marketplace and not a guarantee that a listed server is safe or appropriate for a particular user. MCP: Official Registry

3. Skills

A capable agent may have a filesystem, a browser, shell commands, and external connections and still perform a specialized task inconsistently. Capability answers “what can the system do?” It does not supply a team's preferred method, reference material, templates, or deterministic helpers.

A Skill packages that reusable procedural knowledge in a folder. Anthropic introduced Agent Skills in October 2025 and published the format as an open standard for cross-platform portability in December 2025. In the open format, the folder contains a required SKILL.md and may include scripts, references, assets, or other supporting files. Anthropic: Equipping agents for the real world with Agent Skills; Agent Skills: Overview

documentation-review/
documentation-review/
├── SKILL.md              # trigger description and core procedure
├── references/
│   ├── source-policy.md  # approved source and citation rules
│   └── review-rubric.md  # checks for scope, claims, and pedagogy
├── scripts/
│   └── check-links.py    # deterministic link validation
└── assets/
    └── review-note.md    # reusable review template

Progressive disclosure

A Skill can keep a large body of procedural knowledge available without loading every file into every model call. The common three-level explanation is:

  1. Metadata. A compatible client exposes a short name and description so the model can recognize when the Skill may be relevant.
  2. Core instructions. The full SKILL.md loads when the Skill is activated.
  3. Supporting resources. References, scripts, templates, and other files are opened or executed only when the method calls for them.

The open format describes this staged structure. Exact discovery, automatic activation, manual invocation, and execution controls still belong to the client.

A concrete workflow

Return to the request: “Update the Week 3 page, verify references, and summarize the change.” A documentation-review Skill could guide the existing agent through a repeatable method:

  1. Confirm scope. Identify the named page and read the repository's durable instructions.
  2. Inspect before editing. Read the whole page and its local navigation, references, and neighboring boundaries.
  3. Classify claims. Separate sourced factual claims, teaching synthesis, and product-specific examples.
  4. Load only needed guidance. Open the source policy when adding citations and the review rubric before final verification.
  5. Run deterministic checks. Use the bundled link checker after editing rather than asking the model to simulate HTTP validation.
  6. Report evidence. Summarize what changed, which checks ran, and which decisions remain with the user.

The Skill supplies the method. File and browser tools perform the work. An MCP connection may provide approved external data. Project instructions still supply local rules that apply beyond this one workflow.

Skills versus neighboring concepts

Do not collapse method, capability, and connection
Mechanism Supplies Does not automatically supply
Instruction file Durable project and path guidance. A complete task-specific procedure.
Tool One callable operation or retrieval capability. The team's method for combining operations.
MCP A compatible connection to external capabilities and information. A reusable task method.
Skill A reusable method plus optional references, scripts, and assets. The external connection or every operation it names.

One format, different product behavior

OpenAI documents Skills with project and user scopes, implicit or explicit activation, progressive disclosure, distribution, and optional MCP dependencies. Claude Code adds its own invocation and loading controls. Google ADK provides a framework implementation based on the Agent Skills format, but currently labels that feature experimental. These examples show adoption, not identical client behavior. OpenAI: Build Skills; Claude Code: Extend Claude with Skills; Google ADK: Skills for agents

Skills' evolving frontier

The next frontier is not only writing local Skill folders, but finding, installing, updating, and sharing them. Vercel describes that distribution direction from its own ecosystem perspective, and skills.sh is one concrete searchable directory. Neither source is the Agent Skills specification or an authoritative universal registry. Vercel: Agent skills explained; skills.sh

4. How the pieces relate

The mechanisms surround the Chapter 1 loop; they do not replace it. For the Week 3 update, repository instruction files provide the durable publishing and ownership rules. A documentation-review Skill can provide the optional review method. An approved MCP connection can supply external issue, document, or reference data when needed. The model, tools, and runtime still perform the actual cycles of inspection, editing, execution, observation, and stopping.

MCP and Skills are therefore optional. If all sources are public web pages and the task is one-off, ordinary web access and the user's request may be enough. If the same review process recurs, a Skill may earn its maintenance cost. If approved external systems must expose capabilities across several hosts, MCP may earn its integration cost.

Instruction files and Skills

Always-loaded guidance is more likely to be present when the model needs it; on-demand Skills preserve context but depend on the host or model recognizing when to activate them. A Vercel evaluation found that AGENTS.md outperformed Skills for its own tested task and harness. That result illustrates an activation tradeoff. It does not prove that instruction files universally outperform Skills or that large procedures should always be loaded. Vercel: AGENTS.md outperforms Skills in our agent evals

MCP and Skills

Today, MCP connects external capabilities and information, while a Skill packages a reusable method. The boundary is active rather than frozen: the MCP Skills Over MCP Working Group is exploring how Skills could be discovered, distributed, or consumed through MCP infrastructure. Its charter and in-review work are emerging direction, not settled protocol behavior. MCP: Skills Over MCP Working Group

A compact responsibility map
Mechanism Primary responsibility Typical loading or access path
Instruction files Durable guidance. Loaded through host-specific scope rules.
MCP External capabilities and information. Reached through configured client–server connections.
Skills Reusable procedural knowledge. Discovered and loaded on demand by a compatible client.
