A Map of Modern Agent Systems

A model can generate an answer. An agent system adds a repeatable way to gather information, take actions, inspect results, and continue toward a goal. This guide maps the main pieces without treating any one product as the universal architecture.

Start with a map, not a stack

The terms on this page describe different jobs. Some belong to the agent’s runtime cycle. Some provide capabilities or information. Some organize reusable work. Others control what may happen. A real system may implement them with different names, combine them, or omit them.

Core jobs in an agent system
Concept Primary job
LoopDecides what to do next from the information currently available.
ToolsProvide actions and return observations to the loop.
ContextSupplies the information and instructions available for the next decision.
MCPStandardizes connections to external capabilities and data.
SkillsPackage reusable methods and supporting resources.

One useful test

Ask what job a feature performs. “MCP,” “tool,” and “Skill” may all appear near one task, but they are not three names for the same thing.

1. The agentic loop

The agentic loop is the core behavior: gather relevant context, choose an action, observe what happened, and decide whether to continue. Claude Code’s documentation presents this as gathering context, taking action, and verifying results. The phases blend together in practice. A failed test may send the agent back to inspect a file; a tool result may reveal the next question; a user may redirect the work at any time.

  1. Gather context. Read the request, instructions, relevant files, conversation state, and available capability descriptions.
  2. Decide. Select a next step: answer, inspect, call a tool, ask a question, or stop.
  3. Act. Produce text or request an available action.
  4. Observe. Receive the tool result, error, file change, or user response.
  5. Verify and continue. Check progress against the goal, then repeat or finish.

The loop does not mean “keep going forever.” A useful host gives the agent stopping conditions, a limited capability set, and opportunities for the user to approve or redirect consequential work. The agent can also decide that it lacks required information and ask a focused question. These exit paths are part of reliable loop behavior, not exceptions to it.

Verification deserves its own place in the cycle. Seeing a successful tool response only proves that the action ran. It may not prove that the original goal was met. A coding agent can run tests after an edit; a research agent can check whether each claim has a source; a support agent can confirm that the retrieved record actually matches the user. The appropriate check depends on the task.

This conceptual loop is broader than a particular framework’s runtime. For example, the Google ADK event loop describes how ADK coordinates agents, runners, events, and services. That is one concrete implementation of runtime orchestration; it does not redefine the general idea of an agentic loop.

2. Tools

A tool gives the agent an action it can request: search a catalog, read a page, run a test, query a service, or update a file. The model does not execute the function by merely mentioning its name. The host exposes a callable contract, the model selects it with arguments, the host runs it, and the result returns as a new observation.

Week 2’s find_terms_by_week example made this boundary visible. Its name, description, argument schema, and return shape help the model decide whether and how to call it. Registering the tool gives the agent the capability to execute it. The agent’s instruction then helps set the policy for when the capability should be used. A clear tool contract improves selection and argument construction; it does not guarantee that every output is correct.

PartQuestion it answersWhy it matters
NameWhat action is this?Helps distinguish it from neighboring actions.
DescriptionWhen should it be used?Gives the model selection cues and boundaries.
Input schemaWhat arguments are valid?Constrains the call and makes errors inspectable.
ResultWhat observation comes back?Provides evidence for the next loop decision.
RuntimeWho actually performs the action?Enforces authentication, permissions, timeouts, and failures.

Tool does not imply MCP

A tool may be a local function, a built-in host action, or a remote service adapter. MCP is one connection standard for exposing capabilities; not every tool uses it.

Tool results become context

The return value is not merely a success receipt. It becomes evidence for the next decision. A small, structured result is often easier to use than a large unfiltered dump. Errors should also be explicit: “term not found” and “service unavailable” call for different next steps. The host may shorten or summarize very large results before adding them to the context window, so tool designers should not assume that every returned byte will remain visible indefinitely.

3. Context, instructions, and memory

“The agent knows this” can hide several different mechanisms. The clearest way to reason about them is to ask where the information lives, when it is loaded, and how long it lasts.

Context is the information supplied to the model for its current decision. It can include instructions, recent conversation history, tool results, and retrieved material. Instructions guide the run; history records earlier turns; a tool result is a new observation; retrieval selects external material; memory keeps information available for possible later retrieval; and a Skill is a reusable method whose selected contents may be loaded into context. These are related layers, not interchangeable names for the same thing.

LayerWhat it containsTypical lifetimeImportant limit
Context windowThe information available to the model for its current decision.One model call, assembled repeatedly by the host.Finite; inclusion is not the same as durable storage.

Longer-term memorySelected facts or preferences retained beyond one session.Across sessions, depending on the system.Storage does not guarantee retrieval into the current context.

Project instructions: AGENTS.md and CLAUDE.md

AGENTS.md is an open convention for repository guidance such as build commands, test steps, code style, and scoped instructions. OpenAI’s Customization guide describes it as persistent guidance for Codex, with more specific files applying closer to the working directory.

CLAUDE.md serves a similar purpose in Claude Code: it supplies persistent project or user instructions according to Claude Code’s own discovery and loading rules. Similar purpose does not mean interchangeable loader. Claude Code does not natively discover AGENTS.md; a team that wants one source of guidance must explicitly import, reference, or link it from the convention its product loads.

Context is assembled, not simply accumulated

At each model call, the host assembles a working context from several possible sources: the current request, system instructions, recent conversation, project files, tool descriptions, tool results, loaded Skills, and retrieved memory. The full archive of a project or session is usually larger than the active context window. The system therefore has to select, summarize, or retrieve what matters now.

This distinction explains two common surprises. First, saving something to memory does not guarantee that it will be retrieved for the next task. Second, a file that exists in the repository does not influence the model unless the host or agent reads it. When behavior is confusing, inspect the actual context and event trace before assuming that a rule was ignored.

Keep durable instructions durable

Put stable commands, conventions, and boundaries in project instructions. Put task-specific goals in the request. This keeps the always-loaded layer short enough to remain useful.

4. Model Context Protocol (MCP)

MCP is an open client–server protocol for connecting an AI application to external capabilities and information. In the official architecture, a host application creates a client connection to each local or remote MCP server. Servers can expose three main primitives: tools the model can invoke, resources the application can read, and prompts that package reusable interaction templates.

MCP standardizes the connection and discovery boundary. It is not an agent, a reasoning loop, or a complete application framework. The host still decides which servers to trust, which primitives to surface, how to request approval, and how results enter the model’s context.

Roles in an MCP connection
Role Responsibility
HostThe AI application that manages the user experience, policy, and one or more connections.
ClientThe protocol component inside the host that maintains a connection to one server.
ServerA local process or remote service that exposes selected tools, resources, or prompts.

Google ADK illustrates both directions of the boundary. Its MCP documentation shows how an ADK agent can consume tools from an MCP server and how ADK tools can be exposed through an MCP server. The protocol handles the connection shape; ADK still supplies the agent runtime around it.

What the standard buys you

A shared protocol lets a capability provider describe itself once and lets compatible hosts discover it through a common interface. That can reduce one-off integrations and make local and remote connections feel similar to the agent. It does not remove operational decisions. Someone still owns authentication, transport security, server lifecycle, capability filtering, consent, and error handling. Connecting a server should be treated as granting access to the specific capabilities it exposes, not as installing a harmless description file.

5. Skills

A Skill packages reusable know-how for an agent. The open Agent Skills format starts with a SKILL.md file and may include scripts, references, and assets. Instead of placing every workflow in the always-loaded project instructions, the host can discover a short description and load the full Skill only when it is relevant.

Example directory
release-audit/
├── SKILL.md          # purpose, trigger cues, and procedure
├── scripts/          # deterministic helpers
├── references/       # detailed guidance loaded when needed
└── assets/           # templates or reusable inputs

This staged loading is often called progressive disclosure: first the host sees enough metadata to identify a relevant Skill; then it loads SKILL.md; finally it opens supporting files or runs scripts only when the procedure calls for them. The format specification defines the portable core, while individual products decide discovery, activation, and permission behavior.

QuestionToolSkill
Primary jobPerform an action and return a result.Explain and support a reusable way of working.
Typical contentsCallable schema plus runtime implementation.Instructions, decision rules, scripts, references, and assets.
RelationshipA Skill may tell the agent when and how to use tools.A Skill may include helper scripts, but it is more than one callable action.

OpenAI’s customization model treats Skills as one layer beside AGENTS.md, MCP, memory, and subagents. Claude Code also supports Skills as on-demand capabilities in its extension model. Google ADK now documents Skills support, but labels it experimental; use that implementation with the caution expected for an evolving API.

Choose a Skill when the method is reusable

A good Skill has a recognizable job and a procedure worth applying more than once: preparing a release audit, reviewing a notebook, or creating a source-backed lesson. It should state when it applies, the expected inputs and outputs, and any important safety boundary. Deterministic steps can live in scripts, while judgment and sequencing stay in the instructions. A vague “do everything well” Skill gives the host little help deciding when to load it and gives the agent little operational guidance after activation.

6. Subagents

A subagent is a separate agent invocation given a bounded task. It can use its own context, instructions, and tools, then return a result to a coordinating agent or user. This helps isolate research or parallelize independent work, but it also adds coordination cost. A subagent is not automatically better than a direct tool call: use it when the delegated work needs its own reasoning loop, not merely one deterministic action.

7. Permissions, guardrails, and hooks

These controls answer different questions. Permissions decide whether an action is allowed, often using approval rules or a sandbox. Guardrails check or constrain inputs, outputs, or behavior against a policy. Hooks run deterministic automation at lifecycle points such as before a tool call or after a change. Frameworks may use “callbacks” for related interception and observation points; see ADK’s callbacks and safety guidance. These mechanisms may cooperate, but they are not synonyms.

8. How the pieces work together

Consider a generic request: “Update the Week 3 page, verify its links, and summarize what changed.” One possible system flow is:

  1. Load guidance. The host supplies the request and relevant project instructions such as an AGENTS.md or CLAUDE.md.
  2. Gather context. The agent inspects the existing page, styles, and repository state using available file tools.
  3. Select a method. A documentation-editing Skill may be discovered and loaded because its description matches the task.
  4. Reach an external system. If current issue data is needed, the host may connect through an approved MCP server and expose its tools or resources.
  5. Act. The agent edits the page with a tool. The runtime applies permissions before the action.
  6. Observe and verify. Tool results, link checks, and rendered-page evidence return to the loop as new context.
  7. Respond to controls. A hook may run a formatter; a guardrail may reject unsafe public content; a failed check sends the loop back to revise.
  8. Finish. The agent reports the changed files and remaining uncertainty. Session history retains the exchange according to the host’s policy.

This is a teaching example, not a required stack. The same task might use no MCP server, no Skill, and no subagent. The stable idea is the division of responsibilities: the loop decides, capabilities act, context informs, reusable guidance shapes the method, and controls bound execution.

9. What this chapter does not cover

This chapter establishes vocabulary and relationships. It deliberately leaves the following topics for focused sessions where we can treat them with enough depth:

  • prompting techniques and context engineering;
  • retrieval design;
  • harness engineering and loop engineering;
  • evaluation, tracing, and production observability;
  • deployment, scaling, identity, and cost controls;
  • detailed multi-agent orchestration;
  • how to implement an MCP server; and
  • how to author and validate a focused Skill; and
  • how to distribute and operate production Skills.

Deferring these topics from this chapter is a sequencing choice, not a judgment that they are unimportant. The map on this page gives us shared language for those later discussions.
