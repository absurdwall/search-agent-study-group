Writing Great Skills

A planned chapter on turning a useful method into reusable guidance that an agent can discover, follow, and verify.

Planned scope

This chapter will examine when a Skill is the right abstraction; how its name and description affect discovery; how to separate ordered steps from reference material; how to write checkable completion criteria; and how progressive disclosure keeps the main SKILL.md focused while still making deeper resources available.

We will also need examples and a validation strategy before this chapter becomes a full authoring guide. The chapter number may change as the book develops.

A practical path from a fuzzy idea to reviewed code

Matt Pocock's repository contains a group of Skills that can be read as one delivery path: wayfinder → grill-with-docs → prototype → to-spec → to-tickets → implement → code-review. The repository presents these as composable Skills rather than declaring this sequence as the only canonical pipeline, and smaller work may skip stages it does not need. Matt Pocock — Engineering Skills, pinned commit

  1. wayfinder — find the route. For work too large or foggy for one session, name the destination and maintain a shared map of decision tickets. Resolve the visible frontier until the way is clear; planning, not implementation, is the default outcome. If the whole route is already visible and small, Wayfinder says a map is unnecessary.
  2. grill-with-docs — resolve the hard questions. Run a detailed interview with domain modeling, recording important terminology and architectural decisions as the discussion converges. This turns the follow-up conversation into durable shared context instead of leaving the decisions only in chat.
  3. prototype — make the open question tangible. Before the specification hardens, build throwaway code to answer one unresolved design question. For UI work, compare distinct visual directions; for logic, make state changes driveable and visible. Keep it easy to run and deliberately unpolished, then carry the validated decision—not the prototype code—into the spec.
  4. to-spec — synthesize the agreed design. Turn the conversation and codebase understanding into a specification. It does not restart the interview: it captures the problem, solution, user stories, implementation and testing decisions, and scope already established, then publishes the spec for later work.
  5. to-tickets — cut the spec into executable slices. Produce tracer-bullet tickets that each deliver a narrow, complete, verifiable path through the system. Make blocking edges explicit, review the granularity with the user, and publish the approved tickets in dependency order.
  6. implement — build from the agreed artifact. Implement a spec or ticket, using TDD where possible at the seams agreed during planning. Run focused checks throughout and the full suite at the end, then hand the finished change to code-review.
  7. code-review — compare the result with both promises. Review the diff from a fixed point on two separate axes: Standards asks whether the change follows the repository's engineering rules; Spec asks whether it implements what the originating issue or specification required. The Skill keeps the two reports separate so one kind of success cannot hide the other kind of failure.

Connection to Chapter 3. The workflow turns iterative prompting into explicit handoff artifacts: questions become decisions, unresolved design choices become a throwaway prototype, validated decisions become a spec, the spec becomes bounded tickets, and implementation ends against visible checks. The prompt still matters, but it no longer has to carry the whole project history by itself.

Writing for Agents

Matt Pocock's writing-for-agents Skill is a review reference for any document an agent reads: a Skill, an AGENTS.md or CLAUDE.md file, a spec, a ticket, a runtime prompt, or a document reached through a pointer. Its target is a predictable process—the agent taking the same kind of route each run—not identical output. The packaging changes; the writing problem does not. Matt Pocock — The /writing-for-agents Skill

The guide's default editing move is subtraction. Agent-facing drafts often explain facts the model already knows, adding context load without changing behavior. The more useful question is behavioral: if a sentence disappears, does the agent take a different route? This makes the Skill at least as useful for reviewing an existing document as for drafting a new one.

When to use it. Reach for this reference whenever an agent will read the artifact. grill-with-docs helps decide what the document must know; writing-for-agents helps shape how the document is found, read, and followed.

The two loads

Most authoring decisions become easier when treated as a trade between two budgets:

Context load
The cost of material loaded on every turn: an instruction-file line, a Skill description, or anything else that occupies tokens and attention whether or not the current task needs it.
Cognitive load
The cost paid by the human who must remember which documents exist and when to invoke them. It preserves human judgment, but makes the human the index.

A model-invoked Skill pays permanent context load for autonomous discovery. A user-invoked Skill pays no discovery load, but the human must remember to call it. Splitting, inlining, and progressive disclosure are versions of the same trade.

Five levers for more predictable documents

Context pointers
A pointer must say what material exists and name each distinct branch that should cause the agent to load it. The wording of the pointer, not merely the quality of its target, controls reliable discovery.
Information hierarchy
Keep immediate steps at the top, reference needed by every branch in the file, and branch-specific depth behind pointers. Progressive disclosure protects this hierarchy; it is not only a token-saving technique.
Completion criteria
End each step with a clear and demanding definition of done. The strongest criteria are both checkable and exhaustive, resisting premature completion while requiring the necessary legwork.
Leading words
Reuse compact concepts already familiar to the model—such as tracer bullet or red—to anchor a larger behavior in fewer words. Prefer a strong existing concept over a newly invented label that needs its own explanation.
Pruning
Keep one source of truth, leave easy lookups to the environment, remove stale sediment and duplication, and delete instructions that do not change behavior rather than merely shortening their wording.

A practical review pass

  1. Choose invocation. Decide whether the agent must find the document autonomously or whether a human should deliberately call it.
  2. Sharpen the pointer. Name the material and the genuine trigger branches without repeating synonyms for the same case.
  3. Protect the hierarchy. Keep the active sequence visible and move branch-only reference behind a pointer; co-locate related definitions, rules, and caveats.
  4. Tighten every finish line. Make each completion criterion observable and demanding enough to require the full job.
  5. Prune, then run it. Remove duplication, stale facts, environmental caches, and no-ops. Judge the result by agent behavior, not by document length alone.

It is working if the document becomes shorter without losing behavior, important meanings appear only once, leading words do visible work, and reference needed by only one branch sits behind a pointer instead of crowding the main path.

For the Skill-specific mechanics, the pinned SKILL.md and SKILL-MECHANICS.md preserve the frozen source used to verify frontmatter, invocation, and router-Skill details. The model above remains a practitioner perspective, not the Agent Skills specification.
