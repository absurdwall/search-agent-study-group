Hooks, Guardrails & Evals

An agent can read your instructions and still skip a check, take an unsafe action, or say “done” before the task is complete. How do we make important checks happen—and find out whether they worked?

This chapter teaches three tools for that job: hooks run code at defined moments; guardrails check or limit behavior; evals test the system across repeatable cases. You will learn which hook events to use and how they are configured, choose controls for different risks, and follow an evaluation from a test case to evidence and results.

Chapter 4 covered reusable instructions through Skills. Here we turn to what surrounds execution. Codex and Claude Code provide concrete examples; their APIs are implementations of the ideas, not universal standards.

Examples labeled “illustrative” are teaching scenarios, not recorded demo runs. Configuration examples link to their official sources. Our hands-on Codex demonstrations will be integrated separately.

1. Hooks: make something happen at the right moment

Why use a hook instead of another instruction?

Suppose you want a desktop alert when your agent needs permission. You could tell the model to notify you, but then the model must remember, have the right tool, and choose to use it. A hook attaches that job to the program running the agent.

A hook is a way to run your code when the agent system reaches a defined event. The runtime—the software coordinating the model, tools, and conversation—detects the event and calls the registered code.

The model still decides how to approach the task. The hook lets the surrounding software do something reliably at a supported moment: send an alert, inspect a pending tool call, or run a check after an edit. The event can be predictable even when a model-based check inside the hook is not.

Three pieces you will see in a hook configuration
PieceMeaning
EventWhen? For example, a tool call is about to execute.
MatcherWhich occurrences? A filter might select only calls to an editing tool. The event defines what is matched.
HandlerWhat runs? A command, script, or supported callback that performs the job. A handler can also send information or a decision back to the runtime.
Available eventsPractical usesHow configuration worksInput and decisions

Choose an event for the job

A session is the conversation over time. A turn is one response cycle, which can include many tool calls. Stop concerns finishing a turn; SessionEnd concerns ending the main session. An answer finishing does not mean the session has closed.

How configuration works: a Codex pre-tool check

Goal: inspect a proposed shell operation before it runs. Register a PreToolUse command hook in the project’s .codex/hooks.json. This small example adapts the documented Codex configuration; it shows registration, not a complete policy implementation.

Codex · project .codex/hooks.json · adapted from the official configuration

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "^Bash$",
        "hooks": [
          {
            "type": "command",
            "command": "python3 \"$(git rev-parse --show-toplevel)/.codex/hooks/pre_tool_use_policy.py\"",
            "statusMessage": "Checking shell command"
          }
        ]
      }
    ]
  }
}
Read the example as five decisions
QuestionAnswer in this configuration
Which event?PreToolUse: before a covered operation executes.
What does the matcher filter?^Bash$ matches the complete hook tool name Bash, including Codex’s shell / exec_command path. It selects calls, not text inside their commands.
What does the handler do?Run your Python policy script to inspect the proposed command and decide whether to deny it. $(git rev-parse --show-toplevel) finds the repository root for the script path. statusMessage labels the check while it runs.
Where is it registered?Project .codex/hooks.json; user-wide ~/.codex/hooks.json and inline config.toml hooks are alternatives. Project trust and trust in the exact hook definition are required; the CLI’s /hooks exposes review.
What should happen?If the script returns a supported denial, that pending call is blocked and the agent receives its reason. With no denial, normal permission checks still apply.

The script must exist and actually inspect the operation. A command handler receives event JSON through standard input (stdin) and can return an event-specific JSON decision through standard output (stdout). A crash is not a denial. This matcher covers shell calls; a move-tool policy would match that tool’s MCP name and inspect its own arguments.

Verify the effect: in a disposable workspace, compare an allowed call with a deliberately forbidden one. Check that the handler ran, the forbidden call did not reach the tool, and the agent received the reason. Actual setup and execution belong in the separate Codex demo.

Codex variant: add context at startup or after compaction

A context hook uses a different event and output

This optional user-level ~/.codex/config.toml example prints a reminder and appends it to a local log:

Codex · user config.toml · adapted from the documented schema

[[hooks.SessionStart]]
matcher = "^startup$"

[[hooks.SessionStart.hooks]]
type = "command"
command = "echo 'Startup reminder: inspect the project conventions before editing.' | tee -a ~/.codex/study-group-hook.log"

^startup$ selects a new session. For SessionStart, stdout adds model context; tee -a also leaves a log line to inspect. Use ^compact$ for context restoration after root-session compaction, including continuation within a turn. Review and trust the definition before expecting it to run. This supplies a reminder, not enforcement.

Sources: Codex SessionStart · configuration

Codex completion check: continue the turn without an endless loop

Stop is a completion checkpoint, not session cleanup

After checking real test results or artifacts, a Stop handler can return {"decision":"block","reason":"The required check has not passed."}. Codex uses the reason as a continuation prompt. It does not undo completed actions or close the session.

Inspect stop_hook_active, track attempts, and set a retry limit. A successful command hook must emit valid JSON for this event; plain text is invalid. Completion criteria still need a real checker. SessionEnd is a different, short-lived cleanup event.

Claude Code comparison: format the path reported after an edit

Same job, different payload

The Claude guide supplies this PostToolUse example for .claude/settings.json. It needs jq, Node/npm, and Prettier:

Claude Code · official formatter configuration

{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
          }
        ]
      }
    ]
  }
}

The handler reads tool_input.file_path after a successful Edit/Write call and runs Prettier. Inspect the saved file to verify the effect; no chat message is required. Adapt the short xargs command for arbitrary filenames, including spaces. The matcher does not cover Bash writes.

This is not a drop-in Codex recipe: Codex apply_patch input contains patch text in tool_input.command, even under Edit/Write aliases.

Source: Claude Code Hooks Guide

Protected edits: matchers do not translate tool arguments

A pre-edit policy must parse the actual operation. Claude’s Edit/Write tools expose tool_input.file_path; Codex’s apply_patch supplies patch text in tool_input.command. A matcher such as Edit|Write can select both products’ editing calls without making their payloads identical. It also misses file changes through unmatched tools. Put the authoritative filesystem restriction at the tool or permission boundary.

Sources: Codex Hooks · Claude Code Hooks Reference

What hooks cannot promise on their own

A hook can protect only the actions it covers, at the time it runs. A post-check cannot undo an action, and a failed handler may leave it unblocked. Check these limits before relying on one.

Reference: timing, tool coverage, handler failures, and cloud limits
Before relying on a hook, ask these four questions
QuestionWhy it matters
Did it run before the effect?A post-action check can detect or start a repair. It cannot undo a write that already happened. A background handler cannot hold its triggering action.
Does every relevant path trigger it?Codex local hooks exclude hosted WebSearch; later write_stdin input does not repeat an earlier pre-check. An edit-only matcher misses shell writes.
What happens if the handler crashes?A missing decision is not a successful policy check. Codex errors can leave an action unblocked. Claude command/HTTP failures normally continue; supported onFailure: "block" requires v2.1.295+ and has event-specific limits.
What is being configured?Local Codex hooks are not a general ChatGPT Work API. Cloud orchestration has separate, limited enterprise-managed MCP-hook support. Verify your actual client and execution mode.
Related mechanisms in SDKs

Google ADK calls these interception points callbacks. A Python before_tool_callback can return None to continue or a dictionary to substitute a result, including a refusal. Claude Agent SDK hooks are application callbacks with their own timeout behavior: a pre-tool callback timeout blocks the call, unlike default command-hook failure behavior. The general idea transfers; the response and failure rules do not.

Sources: ADK callback types · Claude Agent SDK hooks

What to take away: A useful hook has a clear job, a documented event, a handler that understands its input, and a test of its effect. For protection, timing, coverage, and failure behavior matter as much as the configuration.

2. Guardrails: decide what must be allowed, checked, or stopped

A hook tells us when code runs. Now ask a different question: what rule do we need, and what can enforce it?

A guardrail is a check or limit intended to keep behavior within a rule. The rule might concern access, an individual operation, content, or a human decision. This is the general concept; a framework’s named Guardrails API implements only particular kinds of checks.

What can implement the rule?

A rule needs a component that can check, refuse, or constrain the action. This practical grouping is not an official universal taxonomy; the mechanisms overlap and can work together.

Choose a mechanism with the information and authority the rule needs
MechanismWhere it acts · example · limitation
Runtime hook / callbackAt a supported event. A pre-tool handler scans a proposed upload and denies it if a secret is found. Use it for timely feedback across matched calls. Coverage and failures matter; a post-check cannot prevent completed effects.
Tool-level validation and enforcementInside the operation’s function or service. A move tool refuses an occupied destination for every caller. Use it for a rule the operation must always obey. Other write-capable tools can still bypass that tool’s restriction.
Permissions, authorization, sandboxingAt an access boundary. A runtime permission rule can deny a tool; service authorization can make a database identity read-only; an OS sandbox restricts a process’s access to files and network destinations. Use these to remove capabilities. Codex’s local command profile does not automatically constrain separately controlled connectors or MCP servers.
Framework validation APIsIn the runner’s validation pipeline. OpenAI Agents SDK input checks can reject requests; output checks can withhold replies; tool checks wrap supported calls. Use these for request/result validation. Parallel checks may allow actions before rejection; classifiers can be wrong, and rejection does not undo actions.
Human approval
Adjacent decision control		At a pause before a sensitive action. Show the publication and destination, then wait for a person’s decision. Use this for human judgment, not automatic proof of safety. Tools still validate; approval must match the payload actually sent.

Primary references: Codex Hooks · ADK safety layers · Codex permission scope · Claude Code permissions and sandboxing · Agents SDK Guardrails · SDK approval workflow

Hook versus guardrail: a hook supplies a place to run code; a guardrail describes the rule-checking or limiting purpose. An alert hook enforces no rule. A tool’s refusal or a service’s authorization policy can enforce one without any Agent Hook.

What does a tool-side rule actually do?

Suppose file A occupies the destination and B is the source. A tool offering move_file(source, destination) can enforce this contract:

  1. Validate the request: check that the source and destination are within the tool’s allowed scope.
  2. Perform a conditional operation: ask storage to move only while the destination is absent. Test that condition as part of changing the files—the mutation—not in a separate preliminary check.
  3. Return the outcome: on a destination conflict, refuse the move, leave A and B intact, and tell the caller to choose another name. This applies even when no Agent Hook ran.

Why checking earlier is insufficient: a hook can see an empty destination, then another process creates A there before the move. A normal replacing move could now destroy A. A no-replace operation must refuse that changed state. Putting exists() inside the tool followed by a replacing move has the same gap.

Implementation references: storage conditions and ADK in-tool policy

A real implementation needs a storage primitive or transaction that couples the condition with the change. On Linux, renameat2 with RENAME_NOREPLACE is one example: an existing destination causes an error. Filesystem support and cross-filesystem moves have limits; this is not a portable API for our demo. Copy-and-delete designs need separate failure/recovery handling.

Google ADK illustrates the same placement principle for a query tool: the application supplies trusted policy through Tool Context, such as select_only and an allowed-table list, and the tool checks model-provided queries against that policy. The model’s arguments do not define its own authority. The documentation’s conceptual query checks are not a complete SQL security implementation; database authorization remains another layer.

Sources: Linux rename / no-replace semantics · ADK in-tool guardrails

One rule, three places to check it

Rule: do not overwrite an existing file. Compare early intervention, later detection, and enforcement inside the move.

These are compatible check locations, not mutually exclusive kinds of guardrail. A system can combine all three: early feedback, operation-level enforcement, and later verification.

Choose by the job: use hooks for timely inspection and feedback, permissions to restrict reachable resources, and tool-side rules for conditions that must hold during an allowed operation. Add framework validators for request/result checks and human review where judgment is needed. These layers complement one another.

What should happen when a check cannot decide?

Design the next step, not just the rejection
ResultExpected response
DeniedDo not execute the covered action. Give a useful reason so the agent can choose an allowed alternative.
Approval pendingKeep the action paused. A notification or absence of an error does not count as approval.
Validator error or timeoutTreat the decision as unknown. Follow an explicit failure policy; do not report that the check passed.
Safe but incompleteRetain the original item and report the remaining work. Preserving a file is not the same as organizing it successfully.

If preserving files is essential, the tool should leave originals intact when validation is unavailable. Limit retries and track completed effects so recovery does not blindly repeat an operation.

The SDK can raise a tripwire exception when a check rejects work. The application handles the failure; it is not an automatic rollback.

What to take away: Use access controls to limit capabilities, hooks for timely intervention, tool rules to constrain operations, and validators or human review at the appropriate boundary. Prevention and detection require different timing; verify the outcome.

3. Evals: test the work, then improve the system

A Skill can work once and fail on the next request. After an edit, it can handle the example you fixed while breaking an older one. How do you find out whether it is getting better?

An evaluation, or eval, runs an agent on defined tasks and judges the evidence against stated success criteria. It tests the system the user actually relies on: model, instructions, tools, runtime, and controls.

Use evals to find recurring failures, compare a change with a baseline (a reference such as the previous Skill version), and catch regressions—problems that return after previously passing. A good result answers a bounded question: which requirements did these trials meet, under these conditions?

ComponentsCodex implementationSkill CreatorResults and improvement

Anatomy of an eval

Keep one small example in mind: organize three files without losing or changing their contents. Two files happen to contain identical bytes. This is a conceptual test case, independent of our unfinished hands-on demo.

The components, applied to the same file-organizing task
ComponentWhat you define or inspect
Case and criteriaTask: move files into the requested folders. Success: preserve every original’s bytes and number of copies, complete the required moves, and leave protected files unchanged.
FixtureA saved starting folder, including both identical files. Restore a fresh copy for every trial; record dependencies, permissions, model, Skill version, and runtime settings.
Runner / eval harnessPrepare that environment, launch the agent, collect evidence, invoke graders, and save results. The agent harness is the runtime managing the model and tools inside each run; the eval harness manages the test around it.
Trial and suiteA trial is one attempt at one case. Repeat it to observe variation. A suite is a collection of cases: normal files, name collisions, duplicates, denied operations, and missing tools.
EvidenceTrace: which moves were attempted and their reported results. Artifacts: the resulting files and report. Final state: actual paths, bytes, and copies, including protected locations.
Grades and resultsRecord each criterion’s verdict and supporting evidence. Compare the same cases against no Skill or a saved earlier version, alongside time, tokens, and failures.

Do not use the agent’s “done” as the answer key. A trace records what the runtime exposes; it does not reveal all reasoning or prove external state. Check the files or external system independently. Missing evidence is an uncertainty to report.

Conceptual foundation: Anthropic · Demystifying evals for AI agents. The organizer case and diagram are our teaching synthesis.

Choose a grader for each question

A grader assesses a requirement. A rubric states the criteria for a judgment. Use several graders when success has several dimensions.

Three grading approaches—not interchangeable guarantees
GraderOrganizer example and limitation
Deterministic codeCompare full content hashes and their counts; verify paths and protected files. Repeatable for the same inputs, but only as good as the check: file count alone misses changed bytes.
Model-based rubricJudge whether categories suit the user’s request, citing the files. Useful for flexible quality criteria; fallible and variable. Calibrate its decisions against human review.
Human reviewInspect usefulness, ambiguous cases, and grader disagreements. Supplies domain judgment, but costs time and also needs clear criteria.

Code tests and agent evals fit together. A unit test can check a move tool’s collision behavior. An agent eval asks whether the agent chooses safe operations, handles a collision, and completes the user’s request. Code tests can grade that larger workflow; testing the tool alone does not test the agent’s decisions.

Try a grader’s evidence question: did all three originals survive?

Keep the original fixture and grader outside the agent’s editable output. Test the checker on known good and bad results. Final files alone cannot prove that no forbidden temporary effect occurred during execution.

See the boundary: a Codex capture command is not an eval runner

With the article’s setup-demo-app Skill available in a fresh disposable repository, this current CLI pattern runs one app-building task and saves its emitted events and errors outside the workspace. It is illustrative, not a recorded run:

Codex CLI · one trial, not a complete Skill-eval harness

codex exec --json --sandbox workspace-write \
  'Use the $setup-demo-app Skill to create a minimal demo app with a header and two cards.' \
  > ../trial.jsonl 2> ../trial.stderr.txt

--json selects event output; workspace-write permits workspace edits. Neither restores fixtures nor defines grades. A surrounding runner must record the exit status, collect artifacts, and apply checks. To test a Skill, make it available and include explicit-use and natural-trigger cases.

The article’s older --full-auto flag is no longer supported in current documentation. Sandbox settings do not guarantee task dependencies, network access, or all needed permissions. The article’s paths, scripts, and schema are examples, not universal Codex requirements.

Current command contract: Codex non-interactive mode

Read a documented command-start event · Codex

For example, the official Codex documentation shows this command event. It is a documentation sample, not output from the app case or our demos:

{
  "type": "item.started",
  "item": {
    "id": "item_1",
    "type": "command_execution",

item.started and in_progress tell us the command began. The item ID identifies that activity. To assess its outcome, find its corresponding completion/result in the captured run and inspect the reported status. Do not grade a command as successful just because its text appears.

Source: Codex’s documented event stream

Why improve a starter grader?

The article’s file-presence check can pass when package.json exists but the app cannot build. Finding npm install in a trace can show an attempt without proving success. Add completed-command checks and an independent build/test when those are your criteria. For our organizer, file count likewise needs content-and-copy checks.

Build tests can grade generated code; they still cover only the behavior those tests exercise. Prefer outcome requirements over one exact sequence of tool calls unless that sequence itself matters.

Skill Creator: a packaged test–review–improve loop

Anthropic’s Skill Creator is a Skill with bundled scripts and grader instructions. It helps Claude coordinate the workflow you have just learned, then puts outputs in front of the author before another revision.

With Skill Creator available, give Claude the target Skill and files, then ask: Use skill-creator to evaluate my PDF Skill. Help me define realistic cases and checks, compare with a baseline, and show me the outputs before revising it.

Define the case inside the Skill

Skill Creator starts with a few realistic prompts, input files, and a description of success; the author reviews them. Checks can be drafted as the first trials run. This compact example uses the official schema, with our own hypothetical non-fillable PDF fixture:

pdf/evals/evals.json · illustrative case, documented format

{
  "skill_name": "pdf",
  "evals": [{
    "id": 1,
    "prompt": "Fill the Name box in name-form.pdf with Ada Lovelace. Save filled.pdf; leave other content unchanged.",
    "expected_output": "A readable PDF with the name inside the Name box.",
    "files": ["evals/files/name-form.pdf"],
    "expectations": [
      "filled.pdf opens with Ada Lovelace inside the Name box.",
      "Other page content is unchanged and unobscured."
    ]
  }]
}
  • skill_name matches the Skill’s frontmatter name; id identifies the case.
  • prompt is the task; files lists inputs relative to the Skill root. You must supply the actual PDF.
  • expected_output describes success. expectations contains statements to grade; it is not executable validation code.

A name found somewhere in the PDF is insufficient. Inspect the rendered page for placement and obscured content, alongside programmatic checks. The test designer must turn “correct placement” into a criterion that the reviewer or checker can apply consistently.

Format: Skill Creator schemas. Workflow prose also calls checks assertions; the per-case eval_metadata.json uses that field name. Follow each file’s schema rather than interchanging the names.

What gets run, graded, and reviewed?

  1. Run both conditions. Each case gets a candidate-Skill trial and a baseline trial in independent contexts. For a new Skill, the baseline has no Skill. For an edit, snapshot the old version before changing it. Keep inputs and conditions comparable; save outputs under separate iteration/case directories.
  2. Grade the outputs. Graders inspect transcripts and files, recording each expectation’s verdict and evidence. The implementation explicitly recommends scripts for checks that can be verified programmatically. A separate, optional blind comparator judges outputs labeled A/B without knowing their source; preference does not mean every requirement passed.
  3. Review before revising. The bundled viewer’s Outputs tab shows prompts, files, formal grades, and feedback. Benchmark shows pass rates, timing, tokens, and per-case analysis. Later iterations can show earlier outputs and feedback.
  4. Improve and re-evaluate. Claude reads the author’s feedback and proposes a generalizable change. Rerun the cases, including baselines, in a new iteration. Add fresh cases instead of only tuning to familiar examples.

What still belongs to the author? Representative cases, meaningful criteria, valid fixtures, review of the actual outputs, and the decision that a change is worth keeping. Skill Creator coordinates and assists; it does not make an inadequate test trustworthy.

A real improvement, reported by Anthropic: evals exposed the PDF Skill’s difficulty positioning text on non-fillable forms. The fix anchored placement to extracted text coordinates. The lesson is to repair the failed technique, not merely add “be accurate” to the instructions. Our JSON case is inspired by that problem; it is not Anthropic’s original case or a reproduced result.

Ask what the rate counts. Skill Creator’s expectation pass rate summarizes passed checks. That differs from the fraction of trials meeting every required criterion. An average can improve while an essential safety check still fails.

A failure is a starting point for diagnosis

Possible findings—not measured results from our demos
EvidenceInvestigate before changing the Skill
The agent chose an overwriteSkill / controls: were collision handling and the tool’s enforcement adequate? Confirm the actual file effect.
The needed tool was denied or unavailableRuntime / environment: was the permission boundary expected? The right result may be a safe refusal and an honest incomplete report.
The output existed before the trialTest setup: the fixture was not reset. Repair the harness and rerun; the apparent pass is invalid.
Three files remain, but a copy was lostGrader: file count missed the requirement. Strengthen and test the checker before claiming improvement.

Make a change justified by the trace and artifacts, then compare using the same cases, criteria, and recorded runtime conditions. Repeat trials and report their count; one lucky pass is weak evidence. If the grader changes, regrade saved evidence when sufficient, or rerun both versions. Scores from different tests are not a clean before/after comparison.

Keep real failures in a regression suite, and try fresh or held-out cases to test generalization. Keep safety, task completion, quality, and cost/time separate. A high expectation pass rate is not the probability of success on all future requests—and a higher score on a weak eval is not proof of a better Skill.

You now have the whole loop: define success, restore the starting state, run trials, capture evidence, grade it, compare, and improve. The tools automate parts of that loop; you remain responsible for whether it measures the work that matters.

4. Put them together: before publishing

Suppose an agent is preparing a GitHub publication. You want useful work to complete without exposing sensitive information. Assign a different job to each mechanism:

One workflow, three complementary jobs
MechanismIts job
HookAt a supported pre-publish action, run a scanner and return a useful refusal when it finds a problem. Confirm that the actual publishing route is covered.
GuardrailsLimit publishing authority, scan the material, pause for required approval, and use relevant Git or host-side protections.
EvalRun known clean and forbidden cases in a test environment. Inspect what was actually published, to which audience, and whether the agent’s report was accurate.

The material matters as much as the timing. A marker removed from the current file may remain in Git’s staged snapshot or an earlier outgoing commit. Inspect the snapshot and history that will leave the machine.

Git details: working files, staged snapshot, and outgoing history
A publication check must inspect the right state
StateWhat to inspect
Working filesWhat is on disk now. A clean file does not establish that history is clean.
Staged snapshotWhat the next commit would contain; it may differ from the working file.
Outgoing commitsEarlier commits being pushed may retain sensitive text even after a cleanup commit.
Remote publicationWhat actually became available and who can access it.

.gitignore does not untrack an existing file. Local Git hooks can have bypass paths, and GitHub push protection has its own availability, supported-secret patterns, and bypass rules. A fake marker such as DEMO_SECRET_DO_NOT_USE is useful for a custom test, but does not test GitHub’s supported-secret detection.

Sources: Git ignore rules · Git hooks · GitHub push protection

What to take away: Hooks connect checks to events. Guardrails determine what can proceed. Evals test whether the whole arrangement behaves as intended, including its failure paths.

Optional: where loops and graphs help

Use them to describe recovery and improvement

Inside a run, a tool result can lead the model to choose another action. A denied filename might lead to a new destination; a failed test might lead to a repair, within a retry limit. Between runs, eval results guide changes to the system. These are different loops.

A graph can make recovery branches explicit: allow → execute; conflict → revise; approval → pause; retry limit → report incomplete. The graph describes routing. Each operation still needs its own checks and permissions.

Practice: can you design and explain one?

Choose a workflow you already use. Answer these questions before adding a hook or calling a test an eval.

A design check you can teach from
QuestionWhat a complete answer includes
What should happen automatically?A concrete job and the event that should trigger it.
What will the handler read and return?The actual product’s input fields and supported response, plus an observable test.
What rule must hold?The control that can enforce it, including other tool paths and validator failure.
How will we test success?A known starting state, request, criteria, captured evidence, and an appropriate grader.
What would disprove “done”?A failed artifact/state check, an incomplete operation, or a report that contradicts the evidence.
A notification hook ran. Was the action approved?

No. The handler sent an alert. The permission decision is separate and may still be pending.

A post-tool check rejected an overwrite. Is the original safe?

The write may already have happened. Inspect the effects and recovery source. Use prevention before execution and a no-replace rule inside the file tool.

The final message and the trace both say the task succeeded. Is that enough?

Inspect the outcome too: files, a reservation, or the remote publication. Recorded claims can disagree with external state.

The eval score improved. Is the system better?

Check that the cases and graders remained comparable, inspect failures and trial counts, and look for regressions in other requirements. The score summarizes selected checks; it does not explain them.
